# 実験手法: この実験系で正しい結論を出すための手続き

本書は**実験を円滑かつ正しく進めるための知見**をまとめる。
海賊ゲームそのものについて何が分かったかは
[`results.md`](results.md) に分けた。

ここに書かれている項目の多くは、**一度間違えて後から気づいたこと**である。
個々の経緯は各ラウンドのレポート（[`reports/`](reports/)）に残してある。

---

## 1. この実験系の性質

### 1.1 パイプラインは完全に決定的である

同じ設定ファイル・同じシードなら、**結果は小数点以下まで完全に一致する。**
`run_experiment.py:102` が `config.get("seed", 42)` を読み、
`train.py:188-191` で numpy・torch・両ベクトル環境に同じ種を配る。

3件で確認済み（試行129＝11、試行137＝10、試行144＝12。
後の2件は6体すべての値が一致）。

**帰結が2つある。**

- シードだけを変えて観測されたばらつきは、**計算機側のノイズではなく本当にシードの効果**である
- **1本限りの結果は「決定的」だが「再現性がある」ではない。**
  何度走らせても同じ値が出るだけで、再現性の証拠にはならない。**変えるべきはシードである。**

### 1.2 高い L では収束しない。評価は常にスナップショットである

L=100 の実験は10000エポックまで回しても首位が入れ替わり続ける（12〜30回）。
最終100エピソードの評価は「学習を止めた瞬間の方策」を測っているにすぎない。

**「以後ずっと安定」という素朴な収束判定は使えない。**
有限の系列は必ず最後の変化を持つため、振動し続ける系列でも
終盤のどこかが必ず収束点として返る。実際、素朴な判定では
収束エポックがどの実験でも**学習長の61〜99%**に現れ、学習長に比例していた。
これは収束の証拠ではなく、収束していないことの証拠である。

**収束判定には「安定区間が全体の一定割合以上を占めること」を必ず課す。**

### 1.3 同一条件のシード間のばらつきは大きい

| 量 | 同一条件内で観測された幅 |
|---|---|
| A の平均報酬 | +1.84 〜 +4.50（宝石5個中2.7個ぶん） |
| A の全期間平均 | +0.278 〜 -2.707 |
| 投票の取り分感応度 | 0.045 〜 0.096 |

**中程度の効果は n=4 では検出できない。**
効果量がこの幅に収まるなら、シードを増やすか指標を変えるしかない。

## 2. 実装上の必須事項

### 2.1 n-step リターンの窓はエピソード最大長以上にする

AEC 環境では、提案から否決確定（$-L$）までバッファ上で最大「生存者数」ステップ離れる。
`n_step=3` のままだと終端報酬が提案・序盤投票の遷移に届かず、**学習が完全に停止する**
（提案可決率が10%前後から改善しない）。

`run_experiment.py` はエピソード最大長 $n(n+1)/2 + n - 2$ を自動設定している。

### 2.2 モデルの保存はエージェントごとに明示的に行う

`MultiAgentPolicyManager.policies` は素の `dict` であって `nn.ModuleDict` ではないため、
**`manager.state_dict()` は空を返す。**

```python
torch.save({agent: policies[agent].state_dict() for agent in agents}, model_path)
```

これに気づかず、しばらくのあいだ**保存されたモデルがすべて空**だった。
読み込み側は空ファイルを `ValueError` で弾くようにしてある。

### 2.3 観測フォーマットは2か所で定義されている

`env.observe()` と `pretrain._build_observation()` の**両方**が観測を組み立てる。
片方だけ変えると、学習は通るのに次元不一致で落ちる
（`mat1 and mat2 shapes cannot be multiplied (1x24 and 26x128)`）。

**観測の形を変えたら必ず両方を直し、スモークテストを走らせる。**

### 2.4 事前学習と票数観測は併用できない

`pretrain.py` は `observe_vote_tally` / `observe_noise_dims` が有効なら
`ValueError` を投げる。一般解ではこれらの次元の目標値を定義できないためである。

**事前学習を含む比較では、両群とも票数観測なしにする。**

### 2.5 学習エポック数は7000を既定にする

- 1000は短すぎる（同一設定の1000と10000が正反対の結論を出した）
- 10000でも収束しないので、延ばす根拠もない
- **エポック数250以上ではバッファ100000・学習率1e-4に張り付く**ため、
  7000と10000の実験はハイパーパラメータが同一で直接比較できる

## 3. 測定指標の設計

### 3.1 離散指標は n=4 では解像しない。連続量に置き換える

0〜5 の整数指標（取り分に反応しない投票者の人数）では、
同一条件のシード間に 2〜5 の幅があり、**平均差 1.0 程度を分離できなかった。**

連続量に置き換えると群が分かれる。実例が2つある。

| 離散指標 | 連続量 | 結果 |
|---|---|---|
| 反応しない投票者の人数（0〜5） | **投票の取り分感応度** | 乱数と票数観測が分離（第22ラウンド） |
| A の順位（1〜6） | **A優位度**（A − 他5体平均） | 8本が完全に2群に分かれた（第29ラウンド） |

第29ラウンドでは、**順位で見れば 3対1 対 3対1 で不明瞭なもの**が、
優位度では範囲が重ならなかった。**指標の選択が結論を分ける。**

### 3.2 報酬は「全期間平均（死亡込み）」を使う

「死亡なし記録点の平均」は、**頻繁に死ぬエージェントほど罰を受けた区間が除外されて
有利に見える。** 実際、試行12 の A は最終評価 +0.01、死亡なし平均 +1.23（1位）、
死亡込み平均 -2.16（最下位）と、指標次第で結論が反転する。

`scripts/summarize_agent_rewards.py` が全期間平均・A優位度・A順位を機械的に出す。

## 4. 判定手続き

### 4.1 実験を始める前に、予測と反証条件をレポートに書く

**これが最も効いた。** 第27ラウンドでは、4本のうち**3本目まで予測どおりに見えていた。**
そこで止めていれば「予測的中」と報告していたが、**4本目が覆した。**
事前に書いていたので、後から解釈を選ぶ余地がなかった。

書くべきものは3つ。

1. **予測**（できれば数値の帯で）
2. **反証条件**（何が出たら外れと認めるか）
3. **判定方法**（どの指標を、どう比べるか）

### 4.2 差を主張するなら、範囲と順位検定の両方を示す

`scripts/compare_cells.py` が、2つのセルについて
平均・範囲・範囲の重なり・Mann-Whitney U・**全順列を数えた厳密な両側 p** を出す。

**重なるなら「判定できない」と書く。** 平均や中央値の向きだけを根拠にしない。

### 4.3 範囲の重なりは、標本を足しても消せない

一度観測された値を後から取り消すことはできないので、
**重なった時点でその比較は「確立しない」で確定する。**
残りの試行は、平均の向きや順位検定を確定させるためだけに意味がある。

### 4.4 n=2 では足りない。n=4 でも足りない比較がある

**n を増やすと差は縮む。** n=2 で見えた差が n=4 で重なった例が3回続いた。
少数シードの差は**系統的に過大に出る。**

推奨は **n=1 → 2 → 4 → 8 のエスカレーション**で、
n=4 で範囲が惜しい（1組だけ重なる等）なら n=8 まで上げる。
n=4対4 の順位検定は両側5%の棄却域が U≦0 と厳しすぎるが、
**n=8対8 なら U≦13 まで許容される。**

### 4.5 事前基準を上書きするなら、上書きした事実と理由を書く

第24ラウンドでは「範囲が重ならないこと」という事前基準を満たさなかったが、
64組中63組が同じ向きで p=0.0003 だったこと、
および n=4→n=8 で差が**縮まずに強まった**ことを理由に、
**基準を上書きして「確立」と判定した。**

**上書きしたこと自体をレポートに明記する。** 黙って基準を変えない。

## 5. 交絡の点検

### 5.1 ラウンドをまたぐ比較では、設定ファイルを読み直す

第1ラウンド（10000エポック）と第2ラウンド以降（7000エポック）をまたいだ比較には、
**注目していた条件とエポック数の両方が動いていた。**
**エポック数だけで A の全期間平均が 0.9 動く。**

**比べる2つの設定ファイルを実際に diff する。** 記憶で「同じはず」と判断しない。

### 5.2 対で走らせる

条件Aの4本 → 条件Bの4本、ではなく **A42 → B42 → A7 → B7 → …** の順に走らせる。
途中で止まっても、常に釣り合った比較が残る。

### 5.3 既存の実験を対照に使えないか先に確かめる

第29ラウンドでは、対照群を新しく走らせる代わりに
**第28ラウンドの4本（同じ重み・同じエポック数・同じ4シード）をそのまま使った。**
12本で済み、同時にエポック数の交絡も外れた。

## 6. 集計と記録

### 6.1 数値を手で写さない

第12〜14ラウンドで、ある試行の値を別の試行のものとして**17か所に書いた。**
以後、集計はすべてスクリプトに寄せている。

| スクリプト | 用途 |
|---|---|
| `scripts/summarize_agent_rewards.py` | 全期間平均・A優位度・A順位 |
| `scripts/summarize_vote_sensitivity.py` | 投票の取り分感応度 |
| `scripts/summarize_selfvote_trials.py` | 自己反対の集計 |
| `scripts/summarize_convergence.sh` | 秩序収束の一覧 |
| `scripts/compare_cells.py` | 2セルの比較と判定 |
| `scripts/reevaluate.sh` | 学習をやり直さずに再評価 |

**新しい集計を2回目にやる時点で、スクリプトに切り出す。**

### 6.2 実験はラウンド単位で回し、ラウンドごとにレポートを書く

1ラウンド = 1つの問い。レポートには**開始時に目的・設計・予測・反証条件**を書き、
試行が終わるたびに追記し、最後に統合結論を書く。

**外れた予測も、途中で書いた誤読も消さない。** 取り消し線と訂正で残す。

### 6.3 長時間ジョブは実測で報告する

学習は数時間かかる。`nohup` はセッション終了には耐えるが**再起動には耐えない**
（実際に1本が再起動で消えた）。稼働状況は記憶ではなく `pgrep -fl` で確かめる。

進捗の監視スクリプトは、**監視開始時点のログ行数を記録してから**
それ以降の行だけを見る。ファイル全体を grep すると、
過去のエラーに再点火して誤報を出す。
